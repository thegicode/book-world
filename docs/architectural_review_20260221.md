# 📑 프로젝트 아키텍처 및 빌드 시스템 분석 보고서 (2026-02-21)

## 1. 개요 (Overview)
본 프로젝트는 특정 프레임워크(React, Vue 등)에 의존하지 않고, **웹 표준 기술(Web Components)**과 **고성능 빌드 도구(esbuild)**를 활용하여 구축된 사용자 중심의 도서 관리 애플리케이션입니다. 성능 최적화와 코드 유지보수성을 동시에 고려한 "Craftsman Style"의 아키텍처를 지향합니다.

---

## 2. 빌드 시스템 (Build System)

### 🚀 핵심 기술: `esbuild`
*   **평가:** 업계 최고 수준의 번들링 속도를 제공하는 `esbuild`를 채택하여 개발 주기(Edit-Refesh)를 극도로 단축했습니다.
*   **구현 특징:** `esbuild.config.js`를 통해 개발(Watch 모드)과 운영(Minify, Sourcemap) 환경을 명확히 분리하여 관리합니다.

### 🎨 성능 최적화 (Performance)
*   **Critical CSS:** 초기 렌더링에 필요한 필수 CSS만 추출하여 인라인화하는 기법을 적용, LCP(Largest Contentful Paint) 성능을 극대화했습니다.
*   **이미지 최적화:** `sharp` 라이브러리를 이용해 빌드 시점에 이미지를 최적화하여 네트워크 비용을 절감합니다.
*   **HTML Minification:** 배포 시 HTML 크기를 최소화하여 전송 속도를 높였습니다.

---

## 3. 프론트엔드 아키텍처 (Frontend Architecture)

### 🧱 컴포넌트 설계: Web Components
*   **방식:** 브라우저 표준인 `Custom Elements (HTMLElement)`를 기반으로 컴포넌트를 클래스 단위로 모듈화했습니다.
*   **장점:** 프레임워크의 생명주기에 종속되지 않는 독립적이고 수명이 긴 코드를 작성할 수 있습니다.

### 🔄 상태 관리: Observer 패턴 (Pub/Sub)
*   **구현:** `Publisher.ts`를 기반으로 한 직접 구현된 상태 관리 시스템을 사용합니다.
*   **흐름:** `BookModel`의 데이터 변화가 발생하면, 이를 구독(Subscribe)하고 있는 각 UI 컴포넌트(`CategorySelector`, `Favorite` 등)가 자동으로 감지하여 부분 렌더링을 수행합니다.

### 📂 관심사의 분리 (SoC)
*   **Model:** 데이터 스키마 및 비즈니스 로직 관리 (`FavoriteModel.ts`, `Store.ts`)
*   **View:** UI 렌더링 및 사용자 이벤트 처리 (`*.ts` 컴포넌트 파일들)
*   **Service:** 외부 API 통신 추상화 (`CustomFetch.ts`)

---

## 4. 백엔드 아키텍처 (Backend Architecture)

### 🛡️ BFF (Backend For Frontend) 패턴
*   **역할:** 클라이언트에서 직접 외부 API(Naver, 도서관 정보나루)를 호출하지 않고, Node.js 서버를 거치는 프록시 구조를 취합니다.
*   **보안:** API Key, Client Secret 등 민감한 정보를 서버 측 환경 변수(`.env`)로 안전하게 관리합니다.

### 💾 데이터 캐싱 전략
*   **구현:** 빈번한 API 호출을 방지하기 위해 도서관 목록 등의 정적 데이터를 로컬 파일 시스템(`libraries.json`)에 캐싱하여 응답 속도를 향상시켰습니다.

---

## 5. 종합 평가 및 제언

### ✅ 강점 (Strengths)
1.  **압도적 성능:** 불필요한 라이브러리 오버헤드가 없어 실행 속도가 매우 빠릅니다.
2.  **표준 준수:** 브라우저 표준 기술을 사용하여 향후 기술 부채가 발생할 확률이 낮습니다.
3.  **최적화 완성도:** Critical CSS, 이미지 최적화 등 실무 수준의 고급 성능 기법이 적용되어 있습니다.

### 💡 향후 개선 제언 (Recommendations)
1.  **테스트 자동화:** 현재 아키텍처가 매우 견고하므로, `Jest` 등을 도입하여 로직(Model)에 대한 유닛 테스트를 추가하면 안정성이 더욱 높아질 것입니다.
2.  **의존성 주입 (DI):** 컴포넌트 내부에서 `bookModel` 싱글톤을 직접 참조하는 대신, 생성자 등을 통해 주입받는 방식을 고려해 볼 수 있습니다. (테스트 용이성 확보)
